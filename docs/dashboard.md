# Dashboard

The dashboard is a read-only tmux session that renders the whole kanban — every registered project's queues, task states, wake logs, schedule, git state and token spend — across fourteen fixed windows plus one drill window per registered project. It reads state from disk and writes nothing back, so you can build it, kill it and rebuild it at any moment, including in the middle of a release.

If you have never seen the board, read this document in order: **Start the board** puts it on screen, **Window tour** is the map, and **The fourteen fixed windows and the per-project drill windows, one at a time** says what each window is for and when you would go there. The two windows a new operator actually lives in are window 0 (`main`) and window 1 (`operator`); the other twelve fixed windows, and the one drill window per registered project, are places you visit when you have a specific question.

Per-pane detail — which script populates each region of each window, and the exact command that reproduces that region's output outside tmux — is a separate reference, `DASHBOARD-PANES.md`, beside this file. Both that document and the window tour below are generated from the same machine-readable layout census, so neither can drift from the session the dashboard actually builds. `DASHBOARD-PANES.md` ships in the repository checkout and is not copied into an installed kanban root; read it from the checkout.

## Start the board

Everything below assumes one thing and nothing else: `PGAI_AGENT_KANBAN_ROOT_PATH` is exported and names your kanban install. Nothing else needs to be set, sourced, or already running.

<!-- doc-lint: skip — builds and attaches a live tmux session; requires a running tmux server and an interactive terminal the harness does not provide -->
```bash
cd "$PGAI_AGENT_KANBAN_ROOT_PATH"
scripts/dashboard/create.sh
```

Expected result: the session is built and your terminal is attached to it, showing window 0 — the header across the top, per-project progress in the middle, a live log tail below, and a queues column down the right. Building the session takes a few seconds; panes that have no data yet render as empty tables rather than errors.

The rest of the lifecycle:

<!-- doc-lint: skip — each command acts on a live tmux session that exists only while the dashboard is running; the harness has no tmux server -->
```bash
scripts/dashboard/detach.sh     # leave it running, return to your shell
scripts/dashboard/attach.sh     # re-attach from any terminal on this host
scripts/dashboard/kill.sh       # tear the session down
```

`Ctrl-b d` detaches too — the standard tmux binding works exactly as it does in any other session. Switch windows with `Ctrl-b <number>` for windows 0 through 9, and `Ctrl-b '` then the number for windows 10 and above.

Killing the session destroys nothing. Every figure on the board is read from files under the kanban root, so a killed dashboard costs you the session and not one byte of kanban state. Kill it before an upgrade; rebuild it after.

## The fourteen fixed windows and the per-project drill windows, one at a time

What each window is for, in creation order. Everything here is orientation: the script behind each pane, and the standalone command that prints that pane's content without tmux, are in `DASHBOARD-PANES.md`.

**Window 0: `main`** — the overview, and where the session drops you. Framework version, clock and global HALT state across the top; per-project progress in the middle; a live tail of the agent logs below; a per-project queues column pinned to the right quarter of the window. If you look at one window while a release runs, look at this one.

**Window 1: `operator`** — window 2 with somewhere to type. Top to bottom, it holds three rows. First comes the same eight-column board at the same widths: BUGS, PRIORITIES and REQUIREMENTS on the left, and the PM, CODER, WRITER, TESTER and CM queues on the right. Below the board is a full-width command-line shell, opened at the kanban root with the kanban environment already sourced. Last is window 2's colour legend bar. The shell takes 15% of the window height and never fewer than three rows, and the window opens with your cursor in it. For a reminder of the common commands, run `scripts/dashboard/suggested-commands.sh` from that shell. This is the window to live in when your only terminal is an attach — over ssh, or inside a container.

**Window 2: `visibility`** — the same eight board columns, read-only, with a colour legend along the bottom. No shell, nothing to type into. This is the display-on-a-second-monitor window: white items are pending, amber are active, green are settled (done or WONT-DO; see "Board status and WONT-DO" below), and each project keeps the colour it was given in the project registry.

**Window 3: `attention`** — a single pane listing the items that want a human: tasks sitting in BLOCKED, with the reason each one recorded. An empty pane here is the healthy state, and it is the fastest question the board answers — "is anything waiting on me?"

**Window 4: `schedule`** — the agents' heartbeat, in two full-width bands, each answering one question. The **list band** on top answers "what did each lane last do, and when does it fire next": one row per agent, in fixed roster order, showing when it last fired, the verdict that firing reached — `completed <N>`, `idle (no BACKLOG)`, `HALT skip` or `contended` — and when it fires next. The list keeps every roster row through a live terminal resize, a first view from a client attached at another size, an explicit `resize-window` and a switch to the window. Its height is re-applied after every size or layout change to the window, except while a schedule pane is zoomed. A band border dragged by hand therefore snaps back, and a short window takes its rows from the event band instead. The **event band** below answers "what has actually happened today", merging every agent's wake log into one chronologic, agent-tagged stream of signal lines only: dispatches, task completions with their state, HALTs, queue promotions, reaped worktrees, error blocks and sweep-census skips. A signal class that declares a collapse identity — the sweep-census skip is the one that does today — is folded across the whole day into a single row per distinct identity, tagged with its occurrence count and first-seen time; a class that declares none renders every occurrence. Idle-cycle boilerplate is filtered out of that stream and repetition is folded within it; neither is discarded — the unfiltered per-agent logs stay readable in window 9 (`logs`) and one agent at a time via `cron-tail.sh <agent>`. Go here when work is not moving and you need to know whether the wake fired at all, and what happened when it did.

**Window 5: `git`** — per-project repository status on the left, recent tags on the right, for every registered project's dev tree. The standalone commands for this window's panes need `PGAI_DEV_TREE_PATH` set in addition to the kanban root; the panes inside tmux inherit it from the session.

**Window 6: `metadata`** — a single pane of project and configuration introspection: what the kanban thinks is registered, configured and resolved. The window you use to answer "is this install seeing the config I think it is?"

**Window 7: `rc-metrics`** — the cost window: today's spend and the in-flight RC on the left, the running history of shipped RCs on the right. It has its own section below, because it is the one window whose columns need explaining.

**Window 8: `agent-metrics`** — per-agent, per-project averages and totals, in two side-by-side panes. Where window 7 asks what this RC cost, this one asks what a WRITER task typically costs on this project. The left pane is the live table over the newest 10 shipped RCs, and it is the window's default view. The right pane is the full-history report over every shipped RC. That split pane is the form that shipped: you don't need to run the report yourself to see it. Each block shows three averages to one decimal (`2.0`, not `2`), then `Total Tokens` and `Total Tasks` columns. A footer such as `window: 10 shipped RCs (2 cancelled excluded)` (example values) states how many shipped RCs the figures rest on and how many cancelled ones were left out. Cancelled RCs never count toward an average. For any other span, run `scripts/dashboard/agent-metrics.sh --all [--project <proj>]` from window 1's shell pane, and narrow it with `--since vX.Y.Z` or `--last N`. That command is also listed by `scripts/dashboard/suggested-commands.sh`, which you run from the same shell. Column meanings are in `DASHBOARD-PANES.md`.

**Window 9: `logs`** — a single pane of the wake logs from every agent, interleaved in time order. The plain "what is the system doing right now" window.

**Window 10: `debug-logs`** — per-project debug-gate output, one pane. Quieter than the wake logs and more specific: this is where the verbose per-agent diagnostic lines land when debug output is turned on for a project.

**Window 11: `training-logs`** — reasoning-trace corpus activity, one pane. It is empty unless trace collection is enabled, and an empty pane here means exactly that.

**Window 12: `terminal`** — a live log stream on the left, an interactive shell at the kanban root on the right. The same shell window 1 has, but with logs beside it instead of the board above it: use it when you are running commands and want to watch their effect land in the logs.

**Window 13: `human-review`** — approvals waiting on a human on the left, auto-resolutions the system applied on its own on the right. The two halves of "what did this system decide without me, and what is it asking me to decide."

**Window 14: `drill-N`** — one window per registered project, from index 14 upward, scoped to that project alone. Release and feature projects get five panes: a project header, its logs, its queues, its progress, and its next cron firings. Document-workflow projects get two: the artifact version library and document-pipeline progress on top, the shared log stream below. Use a drill window when one project is misbehaving and the all-projects views are too crowded to see it.

## Board status and WONT-DO

**WONT-DO renders as one token, `wont-do`, on both the operator API's `GET /board` and the dashboard's board columns.** It is never folded into `done`. A task whose `## State` is `WONT-DO`, and an intake file whose `## Status` is `wont-do`, both classify as `wont-do`.

The closed states are `done` and `wont-do`, and `close.sh` accepts no others. An older file may still carry the retired status `superseded`. It is not rewritten, but the board reads it as `wont-do`: it classifies as `wont-do` and is drawn in the closed green, never in the open white.

The eight board columns in windows 1 and 2 and `GET /board` classify every item through the same classifier, the `pgai_agent_kanban.board` package, so the two surfaces cannot disagree about an item. `GET /board` returns `"status": "wont-do"` for such an item (the full status vocabulary is in the `/board` row of [operator-api.md](operator-api.md), "Structured reads"). The columns draw it in the same green as a done item, because both are settled and need no action.

The colour legend therefore has no separate WONT-DO entry: its green covers both. To tell a declined item from a shipped one, read its status through `GET /board`, or open the item with `scripts/show.sh --project <name> --key <key>`.

## Refresh cadence

A pane renders only while someone can see it. Every pane in the dashboard (the panes listed above and every window the "Window tour" above covers, except the interactive shells) uses this visibility-aware refresh cadence, not a single flat interval.

A pane is **visible** when its window is the session's active window **and** at least one client is attached to the session. Anything else is **hidden**: another window is active, or nobody is attached. A detached dashboard shows nobody anything, so while it is detached every pane in it is hidden and renders nothing.

- **Arrival render**: every pane renders once when it starts, so it always has content to show, visible or not.
- **Visible**: a pane re-renders every `PGAI_DASHBOARD_REFRESH_SECONDS` (default 5 seconds), or at its own fixed interval where it has one.
- **Hidden**: a pane renders nothing after its arrival render. It only re-checks whether it has become visible — one tmux query, no render — every `PGAI_DASHBOARD_HIDDEN_MULTIPLIER` times its visible interval (50 seconds at the default 5-second interval).
- **Refresh on activate**: the activation hook wakes a window's panes the moment that window becomes visible — when you switch to it, and when a client attaches. They repaint immediately, so you never wait out the hidden re-check interval; that re-check is only a safety net behind the hook.
- **Stream panes pause**: the log panes follow their logs continuously instead of re-rendering on an interval. While a log pane is hidden its stream is paused; when the pane becomes visible again the stream resumes and catches up on the lines it missed.
- **Stagger jitter**: panes started together (e.g. the eight columns in the Visibility window) apply a small, bounded, per-pane offset before their first render, so a dozen-plus panes do not all redraw on the same wall-clock beat.

This applies uniformly to every pane running under `cadence-loop.sh` (`$KANBAN_ROOT/scripts/dashboard/cadence-loop.sh`) — every rendering pane, with the log panes running under its `--stream` mode. The hidden re-check multiplier and the jitter bound are named constants in `team/scripts/lib/dashboard_constants.sh` (`PGAI_DASHBOARD_HIDDEN_MULTIPLIER`, `PGAI_DASHBOARD_JITTER_MAX_SECONDS`), not per-pane magic numbers.

**The tmux status line is the one always-on surface.** It runs outside the pane loops and appears on every window. While a client is attached, its bottom line refreshes every `PGAI_DASHBOARD_REFRESH_SECONDS`, whichever window you are looking at. So the HALT state, pending approvals, active deferrals and the clock stay current even while every pane outside the active window is paused. How that line is produced is the next section.

## The bottom status line

**One background loop renders it; tmux only reads the result.** `create.sh` starts `status-bottom-loop.sh` in the background when it builds the session. Every `PGAI_DASHBOARD_REFRESH_SECONDS` (default 5), the loop does two things:

1. It runs `status-bottom.sh` once.
2. If that script printed a line, it stores the line in the session's tmux user option `@pgai_status_bottom`, whatever the script's exit status.

The status format's bottom row is `#{@pgai_status_bottom}`. tmux expands that option without starting any process. The line therefore costs one render per interval, however many terminals are attached and however often the panes redraw.

The loop follows the same visibility rule as the panes:

- **On start.** It renders once, so the line is there the moment you attach.
- **While no client is attached.** It renders nothing and only checks again every interval. Just after an attach, the bar can show the line from before the detach for up to one interval.
- **When the session ends.** The loop exits within one interval, so killing the dashboard leaves nothing running.

The loop handles the renderer's output and errors like this:

- **Empty renders.** A render that prints nothing, because the renderer had nothing to print, failed before printing or was killed, stores nothing. The bar keeps showing the previous line until the next render that prints one, and the log named in the next bullet gets one note naming the renderer's exit status.
- **Renderer errors.** `status-bottom.sh`'s stderr goes to `dashboard/logs/status-bottom.log` under the framework temp root, never onto the bar.

**No dashboard tmux option runs a `#()` job.** tmux re-runs a `#(command)` in a status format, window-status format, pane-border format or title string as a shell job. It does so whenever it redraws that text and the last run is more than a second old. With dozens of panes refreshing, that means nearly every redraw, once per attached client.

`team/scripts/dashboard/lint_tmux_format_jobs.py` holds the line against that. It reads every shell script under `team/scripts/dashboard/` and reports any `tmux set-option`, `set`, `set-window-option`, `setw` or `select-pane -T` line containing `#(`. `run-unit-tests.sh` runs it on every certification run. It is a quality-class check: it records a finding and never fails the run. A new status segment or title belongs in the render behind the loop, or in a loop of its own that writes a user option.

**What the bottom line shows.** On every window the line reads, left to right:

- the install version
- the PM mode
- every active HALT and HALT-AFTER, global first and then projects alphabetically
- pending approvals
- the deferral segments
- the clock

The deferral segments work like this:

- **Kanban-wide deferral.** A deferral set in `kanban.cfg` or a root campaign file reads `DEFER GLOBAL …`. It comes first and counts every project that inherits it.
- **Project deferral.** A project can defer its bugs through its own settings: its own `DEFER-LOW-BUGS` campaign file, or its `project.cfg`. Each such project gets a segment reading `DEFER <project> <=<level>[ until vX.Y.Z] (<n> waiting)`. Projects follow alphabetically.
- **Always visible.** A segment shows even at `(0 waiting)`, so a deferral that is on but holding nothing back is still visible.
- **Unreadable posture.** A posture that cannot be read shows `DEFER CONFIG UNREADABLE: <path>` instead.

The full segment reference, with the rich-mode glyphs and the `NO_COLOR` forms, is the "tmux status bar" section of `DASHBOARD-PANES.md`.

## Shared render snapshots

Several regions of the board render the same underlying data more than once. The operator window's board columns and the visibility window's per-column panes run the same column render; a drill window's queues and progress panes re-scan the project the overview window has already scanned. Those twins share one per-tick snapshot instead of each paying for its own scan, which also stops them disagreeing when two independent scans land on either side of a state change.

**The cache is cooperative, and there is no producer.** No snapshot daemon exists, none is started when the session is built, and none is expected — `ps` will never show one, and that absence is the design rather than a missing piece. Every pane is both reader and writer: the first pane to need a region's content computes it, prints it, and writes the result to the cache for its twins, and every twin that ticks inside the staleness bound prints those exact cached bytes. Twin parity is by construction, not two scans coincidentally agreeing.

**The staleness bound is 5 seconds by default.** A snapshot at or past the bound is treated exactly like a missing one: it is never printed, and the pane renders from source instead. The bound resolves in this order, highest precedence first:

1. `PGAI_DASHBOARD_SNAPSHOT_TTL_SECONDS` in the environment — the per-invocation override, for a test or a one-off session.
2. `snapshot_ttl_seconds` under `[dashboard]` in `kanban.cfg` — the persistent setting for this install.
3. 5 seconds, which is also the default active-window refresh interval.

A value that is not a positive integer falls back to 5 rather than disabling the cache.

**A miss is the normal case, not a symptom.** The default bound equals the default active refresh interval, and a hidden pane does not render at all, so nothing keeps a snapshot warm for a window you are not looking at; the first pane of each cycle routinely finds nothing fresh and renders directly. A missing, expired, or unreadable snapshot costs that one direct render and nothing else: it never blanks a pane, and it never reaches the pane's display.

**The cache is disposable.** Snapshots live in `dashboard/snapshots` under the framework temp root — `/tmp/pgai_kanban_tmp` unless you set `PGAI_AGENT_KANBAN_TEMP_DIR`, or changed `tmp_root` and `tmp_subdir` under `[paths]` in `kanban.cfg`. Each one is written to a temporary file and renamed into place, so a reader always sees a complete snapshot, old or new, never half of one. Delete the directory in the middle of a session and nothing breaks: the next tick misses, renders directly, and recreates it. Killing the session removes the whole dashboard temp subtree, snapshots included.

## Where pane narration goes

A pane's display carries rendered columns and nothing else. Everything a renderer has to say about *how* the render went — a snapshot miss, a cache write that failed, an activation-hook skip — is written to a per-pane debug log instead of being printed.

The split has to be enforced deliberately, because a tmux pane has exactly one display surface: stderr paints the pane just as stdout does. The refresh loop therefore redirects each render's stderr into that pane's log file, and the activation-hook sender writes its narration to the same file rather than printing it onto whichever pane the operator happened to switch to.

One file per pane, under the framework temp root resolved exactly as the snapshot cache above:

```
<temp-root>/dashboard/logs/<window-name>.<pane-index>.log
```

So the fourth pane of the visibility window narrates into `visibility.3.log`. Characters a filename cannot carry become underscores, which is why a per-project drill window's log is named after its window with those substitutions; a renderer running outside tmux, where no pane identity resolves, writes `unknown-pane.log`.

To read them, resolve the temp root and look:

<!-- doc-lint: skip — reads a directory that exists only while a dashboard session is running -->
```bash
tmp_root="${PGAI_AGENT_KANBAN_TEMP_DIR:-/tmp/pgai_kanban_tmp}"

ls "$tmp_root/dashboard/logs/"
grep -h 'dashboard-snapshot' "$tmp_root/dashboard/logs/"*.log | tail -n 20
```

What you will find there:

| Line | What it means |
|---|---|
| `[dashboard-snapshot-debug] <label>: snapshot older than <N>s -- rendering directly (routine expiry)` | The cached snapshot for that region had aged past the bound. The design's normal case, kept at debug volume so it does not bury everything else. |
| `[dashboard-snapshot] <label>: no fresh snapshot (missing or unreadable) -- rendering directly` | No snapshot file at all, or one that could not be read. Expected on a session's first ticks; persistent means the cache is not being kept. |
| `[dashboard-snapshot] <label>: failed to write snapshot for twin readers` | The render succeeded but the cache could not be refreshed, so the twins will miss again next tick. Check that the temp root is writable. |
| `activation-hook-sender: skipping pane <pane> (<id>): not armed yet, signal trap not confirmed installed` | A window switch reached a pane before its repaint-on-activate handler was installed, so that pane was not signalled and repaints at its next hidden-pane visibility re-check instead. |

Three things to know before you go looking.

**A pane that cannot write its log still renders.** If the target cannot be created — an unwritable temp root, a read-only filesystem — the loop drops the narration rather than failing the render. You lose the log lines for that pane, never the columns.

**The logs live and die with the session.** Each file is created when its pane's refresh loop starts and removed with the rest of the dashboard temp subtree when the session is killed, so they are a live diagnostic rather than a history to go back through.

**These are not the agent debug logs.** Window 10 streams the per-agent debug output under `$KANBAN_ROOT/logs/debug/`, which is about what the agents are doing. The pane logs are about what the board's own rendering is doing, and the two never mix.

## rc-metrics window

Window 7: `rc-metrics` is reached with `Ctrl-b 7` and is split into two vertical panes that together cover both the in-flight and historical views of RC cost data.

| Pane | Script | What it shows |
|------|--------|---------------|
| Left | `$KANBAN_ROOT/scripts/dashboard/metrics.sh` | Today's per-project metrics — RCs shipped, wall time, tokens with cache hit %, task count — plus a current-RC block (tasks done, elapsed wall time, tokens so far). Reads `metrics/day/<date>.json` and `metrics/rc/<v>.json`. |
| Right | `$KANBAN_ROOT/scripts/dashboard/show-metrics.sh` | Historical RC metrics from `metrics/history.csv`: the last N release candidates with token totals, cache hit rate, and task counts. |

The per-agent-per-project averages live one window over, in window 8, and are not repeated here.

Both panes refresh on the standard dashboard interval (`PGAI_DASHBOARD_REFRESH_SECONDS`, default 5 seconds) while the rc-metrics window is the one you're looking at. Refresh cadence is visibility-aware: switch to another window, or detach from the session, and both panes stop rendering until the window is visible again, at which point they repaint immediately. See "Refresh cadence" above for the full behavior.

The rc-metrics window is a dedicated view so operators can scan recent-release economics without leaving the dashboard.

### Historical view (right pane)

The right pane runs `show-metrics.sh`, which reads `projects/<name>/metrics/history.csv` and renders the last N completed RCs as a single tabular view. The default is the last 10 RCs.

Columns:

| Column | Source field | Meaning |
|--------|--------------|---------|
| `rc` | `rc` | Release-candidate version string (e.g. `v0.29.15`). |
| `wall_time` | `wall_time_minutes` | RC duration in minutes, measured from `opened_at` to `closed_at`. Renders `--` for any RC whose `wall_time_minutes` field is absent (see below). |
| `blocked` | `blocked_minutes` | Minutes inside that duration the RC could not proceed — parked under a HALT, or stalled on one of its own tasks in `BLOCKED` awaiting a human. Renders `0` for an RC that was never blocked and `-` for a row carrying no value (see below). |
| `input` | `input_tokens` | Total input tokens consumed by every agent invocation for the RC. Comma-separated for readability. |
| `output` | `output_tokens` | Total output tokens produced across the RC. |
| `cache_read` | `cache_read_tokens` | Tokens served from the prompt cache rather than re-billed at the input rate. Higher is cheaper. |
| `hit_rate%` | `cache_hit_rate_pct` | Cache hit rate as a percentage with one decimal place. Computed as `cache_read / (cache_read + input)`. |
| `tasks` | `tasks_total` | Total task folders produced for the RC across all agents. |

Numeric columns are formatted with comma separators (for example, `5,644,879`). Empty cells render as `--` rather than `0` so missing data is visually distinct from a real zero.

### Per-agent sub-view

Pass `--per-agent` to switch the view from history (the default) to a per-agent token breakdown for the **most recent** RC. The script locates the highest-version `metrics/rc/v*.json` file and renders the `tokens.by_agent` block as a table.

Columns:

| Column | Source field | Meaning |
|--------|--------------|---------|
| `agent` | object key | Agent role (`pm`, `coder`, `writer`, `tester`, `cm`, etc.). |
| `input` | `input` | Input tokens that agent consumed during the RC. |
| `output` | `output` | Output tokens that agent produced during the RC. |
| `cache_read` | `cache_read` | Cache-read tokens for that agent. |
| `invocations` | `invocations` | Number of times the agent was woken during the RC. |

Agents are sorted alphabetically. The header reads `RC Metrics: <project> — per-agent (<version>)` so the RC under inspection is unambiguous.

### Wall time

The `wall_time` column reads `wall_time_minutes` from `history.csv`. The metrics pipeline records `opened_at` when CM opens an RC and `closed_at` when CM finalizes it, and the aggregator computes `wall_time_minutes` from the two timestamps for the row the dashboard reads.

A row renders `wall_time` as `--` only when the `wall_time_minutes` field is absent for that RC — for example, an RC that has not yet closed, or an older history row written before both timestamps were captured. A `--` is not a signal that the RC failed or was abandoned; it means only that no wall-time value exists for that row.

### Blocked

The `blocked` column reads `blocked_minutes` from `history.csv`. It counts the minutes inside the RC's own open-to-ship window during which the release could not move at all, and it has exactly two interval sources: a HALT flag covering the project — the fleet-scoped file at the kanban root, or the project's own under `projects/<name>/` — and any task of that RC sitting in `BLOCKED` with `Needs Human: yes`. Each source opens and closes its own interval, so a HALT and a blocked task in flight at the same time do not interfere with each other's boundaries.

Overlapping intervals are counted once. Every interval is first clamped to the RC's `opened_at`/`closed_at` window — a boundary outside the window is cut to the window's own edge, and an interval falling entirely outside it contributes nothing — and then overlapping or touching spans are merged before the total is summed. A HALT and a blocked task covering the same wall-clock minutes therefore contribute those minutes a single time. An interval still open when the RC ships is treated as running to `closed_at`.

**Wall is unchanged.** `wall_time` remains honest open-to-ship elapsed time; `blocked` is a second number printed beside it, never a correction applied to it. Real execution time is Wall minus Blocked, and the subtraction is the reader's to do — which is what lets an RC that straddled an operator ceremony still report the elapsed time it genuinely occupied.

An RC that was never blocked reads a real `0`, never a blank: no blocking observed is a measured result. A row whose `blocked_minutes` cell is empty renders a single `-` — deliberately not wall time's `--` — and when at least one rendered row is missing a value the table prints one footer line, `Blocked tracked from v2.24.0`, below the last row. The left pane's current-RC block prints the same figure beside its elapsed time, reading `0` until the in-flight RC has a ledger reading of its own.

A row with no `blocked_minutes` value is an RC that closed before blocked time was recorded; it renders the dash with that footer note, and no value is reconstructed from logs after the fact. An honest absence is worth more than a derived guess, and a number back-filled from evidence that was never collected for this purpose would read exactly like a measured one.

### Invoking show-metrics.sh manually

The right pane runs `show-metrics.sh` under `cadence-loop.sh` (see "Refresh cadence" above), but the script is also a standalone operator tool. Run it any time you want a one-shot historical view outside the tmux dashboard.

```bash
# Default: last 10 RCs across all registered projects
$KANBAN_ROOT/scripts/dashboard/show-metrics.sh

# Show the last 25 RCs instead of the default 10
$KANBAN_ROOT/scripts/dashboard/show-metrics.sh --last 25

# Scope to a specific project (when the kanban hosts more than one)
$KANBAN_ROOT/scripts/dashboard/show-metrics.sh --project my-project

# Combine the two
$KANBAN_ROOT/scripts/dashboard/show-metrics.sh --project my-project --last 50

# Per-agent token breakdown for the most recent RC
$KANBAN_ROOT/scripts/dashboard/show-metrics.sh --per-agent

# Per-agent breakdown scoped to a project
$KANBAN_ROOT/scripts/dashboard/show-metrics.sh --project my-project --per-agent
```

Useful flags at a glance:

| Flag | Default | Effect |
|------|---------|--------|
| `--project <name>` | all registered projects (iterate-all) | Project whose metrics directory to read; omit to cover every registered project. |
| `--last <N>` | `10` | Show the last N rows of `history.csv`. Ignored when `--per-agent` is set. |
| `--per-agent` | off | Switch to the per-agent token breakdown for the most recent RC. |
| `--history-csv <path>` | derived from project | Override the CSV path (primarily for testing). |
| `--kanban-root <path>` | `$PGAI_AGENT_KANBAN_ROOT_PATH` | Point the script at a different kanban root. |
| `--no-color` | off | Disable ANSI color output. Also disabled when `NO_COLOR` is set or `TERM=dumb`. |
| `-h`, `--help` | — | Print the inline help banner and exit. |

The script exits non-zero with a message on stderr when the requested CSV (default view) or RC JSON file (per-agent view) is missing. This is the expected behavior for a brand-new project that has not yet shipped an RC.
