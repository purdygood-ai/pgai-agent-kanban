# Hands-Free Demo Transcript — v2.3.5

## Purpose

This is the RC artifact the HUMAN-APPROVE gate for v2.3.5 reviews. It
records one real, captured execution of the hands-free demo — the
release's centerpiece — proving the entire quality-class-finding-to-
shipped-release cycle runs end to end with zero operator hands, on top
of production code (never a reimplementation).

The demo is reproducible on demand; it is not a one-off manual script.
The automated, re-runnable proof lives in
`team/tests/integration/test_cm_release_synthetic.py`:

- `TestHandsFreeDemoEndToEnd` — the full cycle below.
- `TestDualChannelForcedHookFailure` and `TestDualChannelForcedGateRefusal`
  — the companion dual-channel fixtures (a forced hook failure and a
  forced gate refusal each emit `error`/`message`/`remedy`).

Reproduce this transcript with:

```bash

  tests/integration/test_cm_release_synthetic.py::TestDualChannelForcedGateRefusal \
```

## What the demo proves

A fixture tree carries a deliberate quality-class finding — a
release-notes-shaped prose file citing a bare internal ledger ID

(`Fixed BUG-0042 in the retry loop`) instead of describing the fix by
substance — alongside an otherwise-green test suite. Run hands-free, the
cycle:

1. **Runners exit 0 with the findings file written.** The fixture runner
   (`team/tests/fixtures/hands_free_demo_runner.sh`) reuses the real
   `scripts/lib/gated_runner_lint.sh` breakage/quality split and the real
   `scripts/lint_comment_provenance.py` provenance lint — not a
   reimplementation — to scan the deliberate finding. The finding is
   quality-class (never fatal): it prints in full, lands in the
   machine-readable findings file, and the runner continues. The
   fixture's own green pytest module still runs and passes. The runner
   exits 0.
2. **TESTER reports PASS/functional citing a filed bug.** A bug is filed
   for the finding (the cite-an-open-bug-or-file-one rule,
   `team/roles/TESTER.md` Step 5c) and a TESTER report cites it in a
   "Lint Findings (non-blocking)" section while recommending `PASS` with
   `Systemic Risk: low` — the report shape a real TESTER agent's Step 9
   output carries.
3. **CM ships FUNCTIONAL.** `cm-release.sh` (the real release engine, not
   a stand-in) reads that TESTER report, applies the real
   `cm_ship_policy` decision matrix, and ships the release with
   release-notes `## Status` `FUNCTIONAL` — with zero operator hands at
   any step.

in plain language alongside the trigger id — no bare, unexplained
internal identifier.

## A real bug the full-suite verification caught

Running these fixtures in isolation is not sufficient proof by itself —
the first version of `hands_free_demo_runner.sh` passed every isolated
run but failed once inside the full `run-integration-tests.sh` suite.
Its nested `python3 -m pytest` invocation (the fixture's own green-test
step) inherited the outer session's `PYTEST_ADDOPTS --basetemp` from the
environment; pytest clears and recreates an explicit `--basetemp`
directory at session start, so the nested session silently deleted the
findings file the outer test had just written, moments after writing it.
The runner now launches its nested pytest with its own disposable
basetemp instead of inheriting the caller's. This is exactly the failure
mode Acceptance 3 ("both gated suites exit 0") exists to catch — an
isolated pass is not the same claim as a full-suite pass.
